# Проверка индекса архива на отдельной БД — 25 октября 2026

Миграция `20261025000000_archive_pagination_index` успешно проверена на одноразовом
PostgreSQL 16.15. В тесте семей по 100 000 человек медианная задержка получения
полного HTML архива уменьшилась на **7,78–13,94%**, задержка reader — на
**8,53–27,56%**. Это локальный тест с прогретым кешем, не измерение Neon или
рендеринга браузера.

Рабочая БД и почта не использовались. Текущие изменения приложения и SQL миграции
сохранены; добавлены только инструменты, тесты их защиты и результаты проверки.

## Проверка миграции и данных

- Полная цепочка из **9 миграций** применена штатным `npm run ci:database`.
- `migrate status`, schema diff и история SHA-256 прошли до замеров и после них.
  Финальный повтор: нет ожидающих миграций, расхождений схемы нет.
- **31/31 PostgreSQL integration-тест** прошёл на отдельной тестовой БД.
- Состав индекса подтверждён: B-tree `(familyId, isArchived, id)`;
  `indisvalid=true`, `indisready=true`.
- Между A/B-фазами сравнивались хеши полного DTO каждой страницы, количество и
  контрольная сумма всех строк Person. Результаты и данные одинаковы.
- Подтверждена работа курсора после восстановления пограничной записи.
- SHA-256 SQL миграции:
  `a84eb87e424bea2cc6d9a55e896c7b5c5bec6d475dc905cbb9a6121c4e9ec97d`.

## Среда и методика

Использован переносимый PostgreSQL из официального архива EDB, без установки
службы. SHA-256 архива проверен по опубликованной контрольной сумме
[EDB](https://github.com/EnterpriseDB/edb-installers/issues/696).
Docker Linux engine не запустился; среда теста отличается от Linux/Neon.

- Windows x64, Intel Core i7-8550U, 8 логических CPU, около 16 ГБ RAM.
- PostgreSQL 16.15, collation `C`, shared_buffers 128 MB, work_mem 4 MB,
  JIT включён; planner switches не менялись, индекс не форсировался.
- **421 000 человек в 24 семьях**. Четыре целевые семьи: 1000/50% архивных,
  20 000/50%, 100 000/90% и 100 000/10%. Ещё 20 семей по 10 000 записей создают
  фон. ID — MD5(family:sequence), перемешаны глобально, без группировки по семье.
- Синтетическая биография — 512 ASCII-байт. Все данные вымышлены.
- A1 → B1 → A2 → B2: без индекса → точный SQL миграции → без → снова с индексом.
  Перед каждой фазой — ANALYZE и прогрев; строки и код приложения одинаковы.
- В фазе на сценарий: 30 reader-замеров и 20 HTTP-замеров. Итого **960 reader**
  и **640 HTTP** измерений. Для каждой стороны таблицы объединены две фазы:
  n=60 для reader, n=40 для HTTP; процентили — nearest-rank.
- Reader: настоящий `getFamilyArchivePage` плюс JSON-сериализация. Query-event
  instrumentation одинаково включена в A и B; события не сохранялись и не
  печатались во время замеров.
- HTTP: собранный Next.js 15.5.28 в отдельном временном каталоге без `.env`, с
  явной тестовой БД. Тестовый пользователь вошёл через обычный `/api/auth/login`;
  auth/role checks не обходились. Измеряется получение **всего HTML**, включая
  SSR и скачивание по loopback; TTFB отдельно записан в JSON.
- EXPLAIN ANALYZE/BUFFERS фактического SQL Prisma выполнялся отдельно от timed
  samples. Это снимки параметризованных планов, не замер передачи результата
  клиенту. [Документация PostgreSQL](https://www.postgresql.org/docs/16/using-explain.html).

При первом запуске четыре фазы прошли, но запись итогового отчёта прервалась из-за
чтения удалённого параметра `lc_collate`. Метаданные исправлены на pg_database;
измерения полностью повторены на заново созданной пустой тестовой БД. Ниже и в
JSON — только завершённый повторный запуск. Добавлены checkpoint-файлы каждой фазы.

## Результаты

Все задержки в миллисекундах. «Глубокая» страница — курсор примерно на 90% архива;
«середина» — около 50%. Читаются 25 строк, отображаются 24 карточки.

| Семья / страница | Reader p50 без → с | HTTP p50 без → с | HTTP p95 без → с | Снижение HTTP p50 |
| --- | ---: | ---: | ---: | ---: |
| 1000, 50% в архиве / первая | 4,08 → 2,62 | 19,98 → 16,63 | 23,46 → 20,61 | 16,8% |
| 20 000, 50% / первая | 3,71 → 2,63 | 20,01 → 16,75 | 23,77 → 19,19 | 16,3% |
| 100 000, 90% / первая | 2,93 → 2,68 | 18,24 → 16,82 | 21,19 → 19,60 | 7,8% |
| 100 000, 90% / глубокая вперёд | 3,03 → 2,69 | 18,63 → 16,71 | 22,31 → 18,40 | 10,3% |
| 100 000, 90% / середина вперёд | 3,08 → 2,70 | 19,04 → 16,69 | 24,25 → 19,13 | 12,3% |
| 100 000, 90% / середина назад | 3,04 → 2,71 | 19,07 → 16,88 | 22,63 → 20,25 | 11,5% |
| 100 000, 10% / первая | 3,57 → 2,65 | 19,26 → 16,57 | 22,47 → 19,25 | 13,9% |
| 100 000, 10% / глубокая вперёд | 3,71 → 2,69 | 18,99 → 16,68 | 21,77 → 19,68 | 12,1% |

Во всех шести крупных сценариях направление улучшения повторилось в обеих парах
A1/B1 и A2/B2; p95 также уменьшился. Между фазами заметен небольшой дрейф,
доверительные интервалы не рассчитывались.

### Планы запросов

Глубокая страница семьи со 100 000 человек и 10% архивных:

| Основной SELECT архивных карточек | Без индекса A1/A2 | С индексом B1/B2 |
| --- | --- | --- |
| Использованный индекс | Person_pkey | Person_familyId_isArchived_id_idx |
| Shared buffer hits | 924 / 924 | 28 / 28 |
| Отфильтровано лишних строк | 887 / 887 | 0 / 0 |
| Execution time, мс | 0,740 / 0,692 | 0,065 / 0,057 |

Поиск первой активной карточки тоже использует новый индекс, как Index Only Scan.
Для маленькой семьи исчезла отдельная сортировка архивных записей. Полные планы
всех трёх запросов reader, параметры и сырые latency samples сохранены в
[JSON](benchmarks/archive-index-2026-10-25.json).

### Стоимость индекса

- Размер: **32 440 320 байт = 30,94 MiB** на данном наборе.
- Два построения на заполненной таблице: **2,664 с** и **3,362 с**.
- Стоимость INSERT/UPDATE и поведение под конкурентными записями не измерялись.
- В миграции обычный CREATE INDEX: он блокирует записи в таблицу на время
  построения, сохраняя чтение. Режим применения к рабочей БД требует отдельного
  выбора; данный тест ничего туда не применяет.
  [Документация PostgreSQL](https://www.postgresql.org/docs/16/sql-createindex.html).

## Ограничения и вывод

Индекс соответствует новым запросам и даёт повторяемое уменьшение задержки в
этом стенде. Ускорение SQL заметнее, чем всего HTTP-ответа: остаются авторизация,
вызовы Prisma, сериализация и SSR. JSON страницы и набор карточек не изменились.

Это прогретый последовательный локальный тест, а не cold-cache, нагрузочный тест
или браузерные LCP/INP. Скорость Neon, сетевую задержку и collation рабочей БД по
этим цифрам предсказывать нельзя. Прикладной код и миграция в этой проверке не менялись.

Дополнительная проверка инструментов: **764/764 unit-теста**, TypeScript и ESLint
прошли. Новые guard-тесты сначала воспроизвели отсутствие helper (RED), затем
прошли вместе с существующими защитами (12/12 scoped GREEN). Независимые code и
database review подтвердили методику и арифметику результатов.

## Воспроизведение и завершение

Инструмент: `npx tsx scripts/archive-index-benchmark.ts`. Требует уже собранное
приложение, пустую одноразовую БД, проверенные миграции и явные flags
`RODOVO_CI_DATABASE=disposable`, `RODOVO_ARCHIVE_BENCHMARK=disposable`.
`TEST_DATABASE_URL` — только 127.0.0.1, нестандартный порт и rodovo_ci_test,
отличный от primary URL. До изменений дополнительно проверяется UUID из
`ARCHIVE_BENCHMARK_TOKEN` в COMMENT БД. `.env` инструмент не загружает.
Существующий файл итоговых измерений не перезаписывается.

HTTP-сервер и PostgreSQL остановлены, тестовые порты освобождены. Временная среда:
`E:/FamilyTree/tmp/archive-index-lab-1792887383987`. Автоматическая проверка
отклонила рекурсивное удаление с единственным объяснением `blocked by policy`;
данные и бинарные файлы оставлены в этом каталоге. Обход запрета не выполнялся.
Рабочая БД, почта и существующие изменения пользователя сохранены.
