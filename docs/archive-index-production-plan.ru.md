# План применения индекса архива к рабочей БД

Дата: 25.10.2026. **План, не разрешение на выполнение. Ничего к рабочей БД не применено.**
Подготовка документа не требует подключения к рабочей БД. Почта вне объёма работ.

## Проверенный артефакт и границы проверки

Миграция: `prisma/migrations/20261025000000_archive_pagination_index/migration.sql`.
SHA-256 исходных байтов:
`a84eb87e424bea2cc6d9a55e896c7b5c5bec6d475dc905cbb9a6121c4e9ec97d`.

```sql
CREATE INDEX "Person_familyId_isArchived_id_idx" ON "Person"("familyId", "isArchived", "id");
```

Это обычный неуникальный B-tree индекс. Файл миграции и его checksum не менять.
Существующий индекс по `familyId` не удалять в этой операции.

На отдельном PostgreSQL 16.15 с 421 000 синтетических записей построение заняло
2,664–3,362 с, размер индекса — 32 440 320 байт. Для семьи со 100 000 записей
HTTP p50 улучшился на 8–14%. См. [отчёт](archive-index-benchmark-2026-10-25.ru.md).
Эти результаты не определяют время построения, свободное место или выигрыш на Neon.
Версия сервера, размер рабочей таблицы, текущая нагрузка и история миграций пока
не проверены. Приложение сохраняет корректность без индекса; меняется скорость.

## Выбранный способ

Основной вариант — согласованное окно обслуживания с остановкой **всех** процессов
записи, неизменённой миграцией и штатным Prisma Migrate из проверенного release-артефакта.
Обычный `CREATE INDEX` блокирует запись в таблицу до завершения построения, разрешая
обычное чтение; другие DDL и очередь блокировок тоже могут влиять на доступность.
[PostgreSQL: CREATE INDEX](https://www.postgresql.org/docs/16/sql-createindex.html).

Полное окно включает резервное копирование, проверки и запас на откат, а не только
несколько секунд лабораторного построения. Если остановка записи неприемлема,
этот вариант не выполнять: сначала отдельно проверить вариант `CONCURRENTLY` ниже.
Текущие незакоммиченные изменения приложения не включать автоматически в выпуск индекса.

## До согласования запуска

Ответственный оператор заполняет карточку операции в защищённом журнале:

| Поле | Требуемое решение |
| --- | --- |
| Цель | Neon project/branch/database и схема, без паролей и полного URL |
| Исполнитель | Оператор, наблюдатель, право отмены операции |
| Окно | Начало, максимальная длительность, крайний срок начала отката |
| Артефакт | Версия приложения, lockfile, Prisma CLI, checksum миграции |
| Копия | Защищённое расположение, ключ шифрования, время снимка, срок хранения |
| Восстановление | Отдельная пустая БД/ветка и изолированное хранилище, измеренный RTO и согласованный RPO |
| Пределы | Таймауты, запас места/квоты, допустимые задержки и ошибки относительно baseline |

Будущая ограниченная диагностика выполняется только после отдельного разрешения
на работу с рабочей БД. Проверить:

1. Точную цель и версию сервера, прямое подключение для мигратора, права владельца
   таблицы, TLS. Секреты брать из одобренного хранилища, не печатать в командах/логах.
2. В истории Prisma успешно применены все восемь предыдущих миграций с ожидаемыми
   checksum; нет незавершённых/ошибочных записей. Ожидает **только**
   `20261025000000_archive_pagination_index`. `migrate deploy` применяет все pending:
   при любом другом составе остановиться и подготовить отдельный план.
3. Рабочая схема соответствует первым восьми миграциям. При сравнении с текущей
   `schema.prisma` единственное ожидаемое отличие — отсутствие целевого индекса;
   любые другие расхождения требуют остановки, а не `db push`.
   Таблица — ожидаемая `public."Person"`, не секционированная;
   индекс с целевым именем отсутствует. При существующем индексе сравнить определение
   и историю, не скрывать расхождение через `IF NOT EXISTS`.
4. Фактические размеры таблицы/индексов, квота и запас под новый индекс, временные
   файлы и WAL, нагрузка/репликация, длительные транзакции и ожидающие блокировки.
   Лабораторные 31 MiB не использовать как оценку требуемого свободного места.
5. Заморожены параллельные deploy/migrate, известны все серверы, workers, cron,
   загрузчики и административные скрипты, способ их остановки и возобновления.

Перед рабочим запуском на изолированной БД повторить **точный операционный путь**
с установленной версией Prisma из lockfile: успешное применение, искусственное
ожидание блокировки, таймаут, проверку каталога/истории и восстановление после сбоя.
Начальные предлагаемые пределы: `lock_timeout=3s`, `statement_timeout=60s`;
это предложения для репетиции, не подтверждённые рабочие настройки.
Подтвердить их действие именно в сессии мигратора. `SET` в соседней psql-сессии
не действует на Prisma; нельзя считать передачу `PGOPTIONS` драйверу Prisma
проверенной автоматически. Не менять глобальные настройки сервера/роли ради запуска.
Если ограничение времени в выбранном пути не доказано — **запуск запрещён до доработки
и проверки способа**, а не выполняется без ограничения ожидания.

До начала рабочего окна также подготовить, независимо проверить и отрепетировать
отдельный rollback-артефакт: новую forward-миграцию удаления, соответствующую Prisma-схему,
ограничения блокировок и проверки после удаления. Хранить его отдельно от основного
release-артефакта: rollback-миграция не должна попасть в pending обычного запуска.
Применение rollback-артефакта требует согласованного решения оператора по карточке операции.

## Резервная копия и восстановимость

Следовать [существующему регламенту](backup-recovery.ru.md). Он описывает упаковку
готовых файлов; `backup-package.ts` сам не делает `pg_dump` и не обеспечивает
согласованность БД с файлами.

1. Остановить запись на всех экземплярах, включая фоновые задачи и очистку медиа;
   дождаться завершения активных транзакций/загрузок. Оставить оператора и наблюдателя.
2. Зафиксировать время, версию схемы и агрегированные контрольные количества строк
   (включая архивные/удалённые) и состояния медиа; не выгружать семейные данные в отчёт.
3. Создать PostgreSQL custom dump совместимой одобренной версией `pg_dump` и
   согласованный снимок всего каталога uploads, включая partial-файлы. Использовать
   одобренный libpq service/password file, а не URL с паролем в аргументах.
   Проверить код завершения, stderr, непустой dump и полноту файлов.
4. Упаковать по регламенту, проверить manifest/SHA-256 после переноса в защищённое
   резервное хранилище с ограниченными ACL и шифрованием. Реальные копии, counts
   и ключи не сохранять в репозитории, `tmp`, чате или публичных артефактах.
5. Восстановить копию в **новую пустую** разрешённую изолированную БД и отдельный
   media root. Проверить схему, историю миграций, контрольные количества и чтение
   файлов. Для интеграционных проверок обязателен `TEST_DATABASE_URL` и штатный
   fail-closed guard; нельзя направлять тестовые/seed/benchmark-скрипты на рабочую БД.
   Изолированная среда не должна отправлять письма или обращаться к рабочим сервисам.
6. Записать измеренное время восстановления. `pg_restore --list` и проверка хешей
   сами по себе не доказывают восстановимость. Если времени окна недостаточно для
   согласованной копии и проверки — перенести операцию, не пропускать этот этап.

Neon PITR/restore point может быть дополнительной защитой только после проверки
фактического retention, квот, прав и процедуры восстановления для данного проекта.
Не считать наличие этой возможности или восстановимость всей пары БД+медиа доказанными.
Существующая синтетическая лаборатория не является резервной копией рабочей БД.

## Применение после отдельного разрешения

1. Подтвердить все условия выше и свежую восстановимую копию; записать baseline
   задержки чтения архива, ошибок и readiness. Не генерировать нагрузочный тест на production.
2. Сохранить остановку записи и freeze deploy. Оператор запускает `prisma migrate deploy`
   только из зафиксированного артефакта с локально установленным CLI, явной одобренной
   целью и проверенными сессионными ограничениями. Не запускать команды из текущего
   изменяемого worktree или через загрузку новой версии пакета.
3. Из второй сессии следить за собственным PID мигратора, `pg_stat_progress_create_index`,
   `wait_event`, `pg_blocking_pids`, возрастом транзакций и ресурсами. Не записывать
   полный SQL чужих сессий, персональные данные, cookies или connection strings.
4. При таймауте, достижении предела окна/ресурсов или превышении согласованных ошибок
   прекратить попытку; не увеличивать пределы и не повторять автоматически.
   При необходимости отменять только подтверждённый собственный DDL через
   `pg_cancel_backend`; не завершать чужие транзакции. Отмена/обрыв клиента не доказывает
   завершение серверной операции: дождаться результата и проверить состояние.
5. Проверить каталог: ожидаемый B-tree по `(familyId, isArchived, id)` в нужной схеме,
   `indisvalid=true`, `indisready=true`, неуникальный, без неожиданного predicate/expressions.
   Проверить успешную запись целевой миграции/checksum, отсутствие других применённых
   миграций и schema drift. `migrate status` один не заменяет сравнение схемы и checksum.
6. Пока запись остановлена, сверить контрольные количества. Через штатную авторизацию
   проверить чтение первой/следующей/предыдущей страницы архива, пустой архив и права
   доступа. Никаких тестовых записей в production. Проверить readiness и ошибки.
7. После успешных проверок возобновить writers по согласованному порядку, снять freeze
   и наблюдать 15–30 минут с оператором. Этот срок — предложение для карточки операции,
   не созданное расписание/автоматизация. Сравнить задержки и ошибки с baseline;
   при регрессии использовать ветку отката ниже. Закрыть журнал фактическими временами.

## Откат и частичные сбои

| Состояние | Действие |
| --- | --- |
| Условия до запуска не выполнены | Не выполнять DDL; исправить план/перенести окно |
| Команда завершилась ошибкой или связь потеряна | Проверить собственную серверную операцию, каталог и `_prisma_migrations`; не предполагать автоматически ни успех, ни отсутствие индекса |
| Индекс отсутствует, есть failed migration | После проверки отсутствия изменений согласовать `migrate resolve --rolled-back` для этой миграции и новую попытку; не удалять строки истории вручную |
| Индекс существует, история не завершена | Сначала проверить полное соответствие определения и valid/ready; затем согласовать reconciliation через `migrate resolve --applied`. Не запускать CREATE повторно и не помечать неполный индекс успешным |
| Индекс и миграция успешно применены, появилась регрессия | Использовать заранее проверенный отдельный rollback-артефакт: новая forward-миграция удаления только этого индекса и схема без соответствующего `@@index`; согласовать применение и повторить проверки |
| Повреждение данных/иной инцидент | Остановка записи и отдельный аварийный план восстановления в новую БД/ветку с согласованным media snapshot и проверенным переключением |

Целевой SQL новой rollback-миграции. Отдельный артефакт теперь подготовлен в
[`operations/archive-index-rollback`](operations/archive-index-rollback/README.ru.md);
он не добавлен в основной `prisma/migrations`:

```sql
DROP INDEX public."Person_familyId_isArchived_id_idx" RESTRICT;
```

Обычный `DROP INDEX` получает `ACCESS EXCLUSIVE` и может блокировать также чтение:
ему нужны отдельное окно и проверенные таймауты. Вариант `DROP INDEX CONCURRENTLY`
требует отдельной репетиции вне transaction block; `CASCADE` не использовать.
[PostgreSQL: DROP INDEX](https://www.postgresql.org/docs/16/sql-dropindex.html).

Исходную успешно применённую миграцию не редактировать и не удалять, её историю
не переписывать. Не использовать `migrate reset`, `migrate dev`, seed или `db push`
на рабочей БД. Не откатывать приватные данные из копии только ради удаления индекса.
При аварийном восстановлении согласовать RPO и судьбу записей после снимка;
не перезаписывать рабочую БД и медиа вслепую.

Механизм reconciliation описан в [Prisma: patching and hotfixing](https://www.prisma.io/docs/orm/prisma-migrate/workflows/patching-and-hotfixing).
Сайт сейчас перенаправляет на документацию v7; применимость точного сценария и
CLI должна быть подтверждена репетицией установленной проектной версии Prisma 6,
без переноса конфигурации v7 в этот проект.

## Альтернатива без остановки записи: пока не готова к запуску

`CREATE INDEX CONCURRENTLY` не является проверенным здесь операционным вариантом.
Он разрешает DML, но делает дополнительные проходы, ожидает транзакции и при сбое
может оставить невалидный индекс; его нельзя запускать внутри transaction block.
Нужна отдельная проверка по документации фактической версии сервера.

Если выбран этот путь: не менять байты уже проверенного migration.sql. Подготовить
отдельный проверяемый операционный артефакт concurrent-создания того же индекса,
исполнить через прямое autocommit-подключение и только после проверки valid/ready
согласовать историю исходной миграции через `resolve --applied`. Сначала репетиция
полного пути, включая ошибку, очистку invalid index, сверку checksum/схемы и отмену.
Параллельный `migrate deploy` запрещён до reconciliation. Никакого автоматического
`IF NOT EXISTS`, повторного создания или ручного изменения таблицы истории.
Этот путь требует отдельного разрешения и не подменяет основной план молча.

## Критерий готовности и результат этой подготовки

Обновление 25.10.2026: подготовлен [отдельный release для PostgreSQL 18.6](archive-index-pg18-release-2026-10-25.ru.md)
с раздельными apply/rollback-наборами и точным совпадением восьми исторических
checksum с ранее прочитанной рабочей историей. Успешно проверены создание,
откат, таймауты и schema diff на отдельной PostgreSQL 18.6. Для будущего выпуска
использовать этот зафиксированный ZIP, а не старый bundle PostgreSQL 16.15 или
изменяемый worktree. Исходные миграции проекта и рабочая история не изменены.

Подготовлен отдельный rollback-артефакт и проведена изолированная репетиция;
результаты и точный способ передачи таймаутов описаны в
[отчёте репетиции](archive-index-rollback-rehearsal-2026-10-25.ru.md).
До рабочего запуска остаются незаполненными рабочие параметры, свежая копия/restore
drill, подтверждение применимости к фактическому Neon и отдельное разрешение.
Подключения, backup, DDL, restore и rollback рабочей БД не выполнялись.
Исходная миграция, приложение, почта и прежние изменения сохранены.
