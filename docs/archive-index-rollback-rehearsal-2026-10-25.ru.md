# Репетиция отката индекса и таймаутов Prisma

25.10.2026. Выполнено только на новом локальном PostgreSQL 16.15, отдельный
кластер на loopback с нестандартным портом, Prisma CLI **6.8.2** из проекта.
421 000 синтетических записей. Рабочая БД и почта не подключались.

## Артефакты

- [Изолированный rollback-bundle](operations/archive-index-rollback/README.ru.md):
  девять исходных миграций побайтно, затем новая forward-миграция удаления индекса;
  снимок схемы отличается только отсутствием `@@index([familyId, isArchived, id])`.
- [Runner](../scripts/archive-index-rollback-rehearsal.ts): переиспользует fail-closed
  guard, требует явный `TEST_DATABASE_URL`, оба disposable-флага и UUID marker
  БД/каталога. До мутаций проверяет пустую БД, её имя, адрес, порт и владение.
- [Машинный отчёт](benchmarks/archive-index-rollback-2026-10-25.json).
- [План рабочего применения](archive-index-production-plan.ru.md).

## Измеренные результаты

Длительности ниже включают запуск Node/Prisma, подключение и учёт миграции;
они не равны времени серверного ожидания блокировки.

| Сценарий | Настройки сессии | Результат | CLI, с |
| --- | --- | --- | ---: |
| CREATE при удерживаемом ROW EXCLUSIVE | lock 3s, statement 60s | 55P03; индекс отсутствует | 5,817 |
| CREATE при той же блокировке | lock 3s, statement 1s | 57014; индекс отсутствует | 3,600 |
| CREATE после снятия блокировки | lock 3s, statement 60s | индекс valid/ready, правильный B-tree | 8,748 |
| DROP при удерживаемом ACCESS SHARE | lock 3s, statement 60s | 55P03; индекс сохранён | 6,456 |
| DROP при той же блокировке | lock 3s, statement 1s | 57014; индекс сохранён | 3,398 |
| DROP после снятия блокировки | lock 3s, statement 60s | индекс отсутствует | 2,023 |
| Исполнение `pg_sleep(5)` в отдельной probe-миграции | lock 3s, statement 1s | 57014 во время исполнения | 3,052 |

После каждой неуспешной CREATE/DROP-попытки проверялось состояние индекса, затем
исполнялся штатный `migrate resolve --rolled-back` только для этой попытки.
После снятия блокировок повторный deploy завершился успешно. В истории остались
четыре отменённые попытки и десять успешных миграций; checksum всех активных
записей совпали с SQL артефакта. История не редактировалась вручную.

После успешного отката: 421 000 строк сохранены; агрегированный fingerprint
всех полей Person совпал с исходным. `migrate status` прошёл; `migrate diff`
между БД и rollback-схемой не нашёл различий, включая остальные индексы.
Повторный deploy — no-op. Probe-миграции существуют только во временной лаборатории;
в машинном отчёте основная история зафиксирована до их выполнения.

## Подтверждённый способ передачи таймаутов

В явном URL **прямого подключения**, передаваемом дочернему процессу как
`DATABASE_URL`, параметр `options` формировался через `URL.searchParams.set`:

```text
-c lock_timeout=3s -c statement_timeout=60s -c application_name=index_rehearsal
```

`URL` выполняет кодирование параметра; полный URL и credentials в отчёт не выводятся.
Это поддерживается [коннектором Prisma v6](https://www.prisma.io/docs/orm/v6/overview/databases/postgresql).
В отдельной миграции проверены `current_setting('lock_timeout')::interval` и
`current_setting('statement_timeout')::interval`: именно **3 секунды и 60 секунд**.
Уменьшение statement timeout до 1s использовалось только для контролируемых ошибок.
Истечение 60 секунд на длинной операции отдельно не ожидалось: значение 60s
подтверждено внутри сессии, механизм отмены исполнения проверен с лимитом 1s.

`PGOPTIONS` для дочернего процесса был пустым; его действие на Prisma не предполагается.
Глобальные настройки PostgreSQL/ролей не менялись. Отдельная psql-сессия не использовалась
для установки лимитов мигратору. У лаборатории свой `package.json`, чтобы Prisma
не искал `.env` проекта; явный тестовый URL передаётся до импорта клиента.
Runner дополнительно отвергает вывод CLI о загрузке `.env`.

## Ограничения и завершение

Первый прогон остановился на конфликте уникальности синтетической фикстуры:
исправлены имена записей. Следующий выявил ошибку сравнения строк `60s` и `1min`:
сравнение исправлено на длительности. Итоговый прогон выполнен на новой пустой БД,
старые тестовые состояния не очищались и не подменяли итоговые результаты.

Независимое ревью TypeScript и артефакта не нашло блокирующих замечаний. У runner
есть внешний watchdog 30s; если он сработает, завершение Node CLI на Windows
не доказывает завершение дочернего schema-engine или DDL. До повтора обязательно
проверить собственную серверную операцию и остановить подтверждённый тестовый кластер.
Этот runner — лабораторный инструмент, не сценарий автоматического запуска на Neon.

Итоговые проверки: `npm test` — **766/766**, `npx tsc --noEmit --incremental false`
и `npm run lint` — успешно; `git diff --check` — без ошибок пробелов.
Production build и UI-прогон не выполнялись: изменены операционные артефакты,
лабораторный runner, тесты и документация, код приложения не менялся.

Тестовый PostgreSQL после проверки остановлен, listener освобождён. Синтетические
файлы оставлены в `tmp/index-rollback-lab-1792889629472`; они не являются backup
рабочей БД. Рабочее применение всё ещё требует проверки фактического Neon,
подготовленной копии с восстановлением, согласованного окна и отдельного разрешения.
Штатные исходные миграции, код приложения и пользовательские изменения не изменялись.
