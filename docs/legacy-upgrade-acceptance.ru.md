# Приёмка обновления заполненной старой схемы

Цель: проверить переход с первых двух миграций проекта на текущую схему,
сохраняя синтетические данные. Это продолжение интеграционной приёмки этапа 8,
а не функциональный этап GENEALOGY-01 из исходной дорожной карты.

## Стенд и границы

Используется отдельный одноразовый PostgreSQL 16 на `127.0.0.1:55432`, база
`rodovo_ci_test`, tmpfs вместо постоянного тома. Контейнер принадлежит только
этой проверке. Рабочие данные и учётные записи не копируются; миграции рабочей
БД не запускаются. Никаких reset, migrate resolve или изменения старых SQL.

## Проверяемые свойства

1. Данные сначала действительно существуют в старой схеме: без новых колонок.
2. Полная цепочка миграций применяется штатным Prisma migrate deploy.
3. Сохраняются идентификаторы, исходные значения, связи, роли, счётчики и аудит.
4. Старые пользователи получают legacyAccount=true и sessionVersion=0;
   emailVerifiedAt остаётся пустым. Новые пользователи имеют legacyAccount=false.
5. Старая действующая сессия читается текущей логикой, просроченная отклоняется.
6. Старые parent/spouse связи имеют origin=manual, version=0; миграция не
   достраивает родительство и не создаёт неизвестных людей.
7. Старые медиа остаются ready, без выдуманной checksum и без потери метаданных.
8. Люди и истории получают version=0, истории не становятся удалёнными.
   Шаблонная хронология классифицируется, произвольные подписи сохраняются.
9. История миграций, checksum и схема совпадают с файлами проекта.

## Что эта проверка не подтверждает

Размер и распределение реальной БД, длительность блокировок при production
объёме, смешанную работу старого и нового серверов, наличие реальных файлов,
доставку почты, браузерный вход и восстановление backup. Выпуск требует
отдельного решения и выполнения эксплуатационного регламента.

## Результат

Прогон завершён 30 сентября 2026 на PostgreSQL 16.15, Docker Engine 29.7.2,
Node 22.19.0 / npm 10.9.3.

- `npm run test:upgrade`: **PASS**, код выхода 0; переход **2 → 8 миграций**,
  сохранение всех исходных столбцов и строк **11 таблиц**. Лог:
  `tmp/stage9-upgrade-final.log`.
- Fixture: 1 старый пользователь, 2 сессии, 1 семья, 1 owner-участник,
  1 задача, 3 человека (включая архивного), 2 связи, 1 история, 4 события,
  2 медиа и 1 запись аудита. После обновления добавлен новый пользователь
  для проверки default legacyAccount=false. Персональные и семейные счётчики
  содержат ненулевые значения и сравниваются без изменений.
- Действующая старая сессия принимается текущей `readValidSession`, истёкшая
  отклоняется. Проверены все перечисленные новые значения по умолчанию,
  отсутствие автоматического достроения и пустые новые служебные таблицы.
- Проверены schema diff, checksum/history и повторный `migrate deploy`:
  повторное применение не меняет данные.
- Повторный запуск всей команды на заполненной базе отклонён на этапе
  `empty-database check`, ожидаемый exit 1; `tmp/stage9-upgrade-nonempty-final.log`.
- Изолированная регрессия запуска без disposable-разрешения: **1/1 PASS**.
  TypeScript, ESLint и diff check прошли. Независимый database/code/TypeScript
  review — APPROVE, обязательных замечаний нет.

Первый прогон прошёл проверки данных, но завершился ошибкой после вывода PASS
при финализации. Исправлено: PASS выводится после успешной очистки, удаление
временных файлов имеет ограниченные повторы для Windows; ошибки показывают
только фазу и безопасный код. Повторный прогон завершился с exit 0, временных
каталогов не осталось. Исходная причина первого сбоя очистки точно не установлена.

Одноразовый контейнер `rodovo-stage9-test` остановлен и удалён после проверки
его ID и label; порт 55432 свободен. Рабочая БД не затронута.

## Повторение

Команда `npm run test:upgrade` требует новую пустую `rodovo_ci_test` на loopback,
явные `TEST_DATABASE_URL` и `RODOVO_CI_DATABASE=disposable`. Основной DATABASE_URL
нужно переопределить недоступным тестовым URL, отличным от TEST_DATABASE_URL.
Используется тот же строгий guard, что в `ci:database`. Скрипт оставляет
синтетические строки в одноразовой БД для диагностики; reset и очистку чужих
таблиц не выполняет. После проверки удалить только выделенный контейнер.

Скрипт копирует схему и оригинальные SQL во временный каталог, сначала оставляет
первые две миграции, затем добавляет остальные. Подпроцессы получают только
явно заданный тестовый datasource; их вывод не раскрывается. Новых production
миграций, изменений бизнес-логики и установки зависимостей не потребовалось.
