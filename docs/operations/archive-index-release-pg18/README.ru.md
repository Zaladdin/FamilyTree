# Release-артефакт индекса архива для PostgreSQL 18.6

Дата подготовки: 25.10.2026. Это изолированные снимки миграций и Prisma-схемы,
а не разрешение на рабочее применение. Рабочая БД и почта при подготовке не используются.

## Два отдельных набора

- `apply/schema.prisma` и соседний `apply/migrations`: восемь исторических
  миграций и `20261025000000_archive_pagination_index` — только создание индекса.
- `rollback/schema.prisma` и `rollback/migrations`: те же девять миграций и
  новая forward-миграция `20261025010000_rollback_archive_pagination_index`.
  Схема отличается только отсутствием `@@index([familyId, isArchived, id])`.
- `baseline-checksums.json`: восемь checksum из уже выполненной read-only
  диагностики от 25.10.2026, без endpoint, credentials и семейных записей.
- `manifest.json`: SHA-256 каждого файла артефакта, кроме самого manifest.

Основной `prisma/migrations`, старый rollback-bundle и пользовательская схема
не изменены. Новый DROP не попадает в обычный deploy из корня проекта.

## Согласование checksum

У копии `20260928000000_direct_sibling_relationship/migration.sql` в обоих наборах
переводы строк CRLF заменены на LF. SQL и комментарии сохранены. Полученный SHA-256
`efdb04e0d3fab50f81d3370c45a841be3a7a29a1c1ba1ea746680e6bdb3c4bfe`
точно совпадает с ранее прочитанной рабочей историей. Все остальные SQL скопированы
побайтно; массовой нормализации строк нет. История рабочей БД не переписывается.

CREATE SHA-256: `a84eb87e424bea2cc6d9a55e896c7b5c5bec6d475dc905cbb9a6121c4e9ec97d`.
DROP SHA-256: `86f1956386e23ec112157dbcb0f8ceae0116c7aa6c8635986a7fd1c6e097d502`.

После подготовки считать эти файлы замороженными. При переносе/извлечении проверять
manifest по **байтам**. Локальный `.gitattributes` отключает преобразование текста
для точного сохранения смешанных LF/CRLF; редактор и упаковщик тоже не должны
менять переводы строк. Manifest обеспечивает целостность относительно проверенного
экземпляра, не цифровую подпись. При новых изменениях приложения/схемы требуется
новый проверенный release, а не автоматическое смешивание снимка с текущей веткой.

## Условия будущего запуска

Применять только после отдельного разрешения и выполнения
[операционного плана](../../archive-index-production-plan.ru.md): свежая восстановимая
копия БД+медиа, окно обслуживания, остановка всех writers, наблюдение и запас на откат.
Обычный CREATE блокирует записи, обычный DROP — также чтение; это не concurrent-вариант.

Перед CREATE в рабочей БД должны быть ровно восемь ожидаемых успешных исторических
миграций, совпадающих с `baseline-checksums.json`; единственная pending — CREATE.
Перед DROP — девять ожидаемых успешных миграций и единственная pending — DROP.
Проверить отсутствие failed/unknown/duplicate history, определение индекса и отсутствие
неожиданного drift. `migrate deploy` применяет **все** pending: при другом исходном
состоянии остановиться, не пытаться «исправить» его deploy/reset/seed/db push.

Использовать установленный Prisma CLI **6.8.2** и зафиксированный lockfile проекта,
не скачивать CLI через `npx`. Путь схемы выбирает набор миграций:
`apply/schema.prisma` для CREATE, `rollback/schema.prisma` для DROP.
Полный deploy-командный сценарий с production credentials сюда намеренно не включён.

Запускать мигратор из изолированной рабочей директории со своим `package.json`,
без `.env` и автоматического поиска `.env` проекта. Передавать только явный
одобренный `DATABASE_URL` дочернему процессу; не печатать URL или секреты.
Pooled Neon endpoint не использовать для сессионных options: диагностика показала,
что он отклоняет эти startup-параметры. Требуется прямой endpoint той же разрешённой БД.

В URL через `URL.searchParams.set('options', ...)` передавать
`-c lock_timeout=3s -c statement_timeout=60s -c application_name=rodovo_index_release`.
Проверять сессионные значения выбранным проверенным способом; `SET` в другой
psql-сессии и `PGOPTIONS` не считаются доказанной передачей параметров Prisma.
Глобальные настройки сервера/ролей не менять. Это пределы сессии, а не обещание
полной длительности команды, включая Node, подключение и журнал миграций.

При ошибке сначала сверить каталог, активную серверную операцию и историю, затем
согласовать штатный `migrate resolve --rolled-back`/`--applied` для фактического
состояния. Не редактировать `_prisma_migrations` вручную и не запускать слепые повторы.
После CREATE проверить индекс valid/ready, checksum, схему и чтение архива;
после DROP — отсутствие только целевого индекса, сохранность данных и no-op deploy.

После фактического отката новая forward-миграция должна войти в согласованную историю
следующего release. Возврат индекса после отката — ещё одна новая миграция, а не
переписывание исходной CREATE/DROP истории.

## Проверка артефакта

Тест `tests/archive-index-release-pg18.test.ts` проверяет manifest, согласованные
исторические checksum, неизменённые CREATE/DROP, отдельные наборы и единственное
различие схем. Результат репетиции PostgreSQL 18.6 фиксируется отдельным отчётом
в `docs/benchmarks`; его наличие и успешный исход проверяются перед рабочим запуском.
Этот README сам по себе не утверждает успешную репетицию или готовность backup.
