# Изолированный rollback-артефакт индекса архива

Подготовлен 25.10.2026. Этот каталог — отдельный снимок Prisma-схемы и истории
миграций для проверки и согласованного отката. Он **не подключён** к обычному
`prisma/migrations`; новая DROP-миграция не должна попасть в основной release
создания индекса. Подготовка артефакта не является разрешением на рабочую БД.

## Состав и ожидаемое исходное состояние

- Первые девять миграций и `migration_lock.toml` скопированы побайтно.
- В `schema.prisma` удалена только строка `@@index([familyId, isArchived, id])`
  модели `Person`; остальные пользовательские изменения сохранены в снимке.
- Новая forward-миграция `20261025010000_rollback_archive_pagination_index`
  удаляет только `public."Person_familyId_isArchived_id_idx"` с `RESTRICT`.
- Перед откатом все первые девять миграций должны быть успешно применены с
  ожидаемыми checksum, целевой индекс должен существовать с правильным определением,
  а единственной pending-миграцией должна быть новая DROP-миграция.

Нельзя применять bundle к пустой или частично обновлённой рабочей БД: `migrate deploy`
применяет все pending, включая девять исторических миграций. Нельзя автоматически
смешивать этот снимок схемы с будущими изменениями основной ветки.

## Команды мигратора

Выполнять только установленный в проекте Prisma CLI из зафиксированного lockfile,
без `npx` с возможной загрузкой пакетов. Пример вызова из корня `E:\FamilyTree`
после подготовки **явной разрешённой изолированной среды**:

```powershell
& node .\node_modules\prisma\build\index.js migrate status --schema .\docs\operations\archive-index-rollback\schema.prisma
& node .\node_modules\prisma\build\index.js migrate deploy --schema .\docs\operations\archive-index-rollback\schema.prisma
```

Эти команды сами не являются защитой окружения: Prisma может загрузить `.env`.
**Не запускать их в обычной оболочке с неявным DATABASE_URL.** Для репетиции
использовать `scripts/archive-index-rollback-rehearsal.ts` с явным `TEST_DATABASE_URL`, проверкой
loopback/disposable-цели и ownership marker до любых мутаций; runner должен передать
тестовый URL как `DATABASE_URL` дочернего процесса и исключить рабочие credentials.
Не печатать URL/пароли в логах. Почту и рабочие внешние сервисы не подключать.

Обычный DROP требует `ACCESS EXCLUSIVE` и может блокировать чтение и запись.
Перед применением нужны остановка writers, отдельная наблюдающая сессия и проверенные
именно для сессии мигратора `lock_timeout`/`statement_timeout`; `SET` в другой сессии
не действует. Не применять глобальные настройки сервера/роли ради операции.
Не добавлять `CASCADE`, `IF EXISTS` или `CONCURRENTLY` без отдельного review и репетиции.

После успеха проверить отсутствие только целевого индекса, сохранность данных и
остальных индексов, успешную запись новой миграции, checksum исторических миграций,
соответствие итоговой схемы этому bundle и работоспособность чтения архива.
Повторный deploy должен быть no-op. При ошибке проверить каталог и историю до
повтора; не удалять строки `_prisma_migrations` и не переписывать исходную миграцию.

## Рабочий запуск и дальнейшая история

Рабочий запуск не разрешён текущей задачей. Он потребует отдельного согласования,
свежей восстановимой копии БД+медиа и выполнения
[операционного плана](../../archive-index-production-plan.ru.md).

После фактического рабочего отката новая forward-миграция и схема должны стать
согласованной историей следующего release; основной снимок с девятью миграциями
больше не соответствует такому окружению. Не пытаться повторно применить исходную
CREATE-миграцию и не изменять её checksum. Возврат индекса после отката — ещё одна
новая проверенная forward-миграция, а не удаление истории отката.
