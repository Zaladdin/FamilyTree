# Родово / FamilyTree — аудит проекта

Дата: 28 сентября 2026. Основание: текущая рабочая копия `E:\FamilyTree`, HEAD `eeba376` вместе с незакоммиченными изменениями. Связанный документ: [подробное техническое задание](technical-specification.ru.md).

Уточнение требований после аудита: пользователь установил автоматическое родительство на основании супружества и sibling с возможностью последующего исправления. Оценка A04 и связанные рекомендации приведены к этому правилу; исходный код приложения в рамках уточнения не менялся.

## 1. Вывод

Это уже функциональный прототип семейного архива, а не только макет дерева. Сохранять существующую архитектуру и интерфейс разумнее, чем переписывать приложение. Основной следующий этап — надёжность хранения, исправление фактических ошибок, завершение редактирования данных и безопасное приглашение родственников.

По результатам проверки нельзя рекомендовать публичный запуск текущей версии: установлен Next.js 15.3.3 с известными опубликованными проблемами безопасности; найдены дефекты идентификаторов, обработки дат и несогласованное автоматическое родительство в API и формах. Успешные unit-тесты сами по себе не проверяют эксплуатационную готовность.

## 2. Объём и ограничения анализа

- Инвентаризированы 11 страниц, 15 API route-файлов, 40 unit test-файлов и 2 integration test-файла. В выбранных каталогах найден 151 файл TS/TSX/Prisma/SQL/Markdown до добавления этого отчёта.
- Проанализированы архитектура, основные пользовательские сценарии, маршруты API, сессии и роли, модель данных, запись графа, медиа, журнал, тестовая инфраструктура, миграции и эксплуатационная документация.
- Проведены независимые проверки безопасности/данных, продукта/UI и качества/эксплуатации специалистами ECC. Использованы production-audit и blueprint; repo-scan оказался установочным указателем на внешний инструмент и не запускался.
- Секреты и `.env` не открывались, подключений к реальной БД и операций над семейными данными не выполнялось. Исходный код приложения не изменялся.
- Актуальность уязвимостей проверялась по официальным публикациям React/Next.js. Эксплуатация уязвимостей не выполнялась.
- Это комплексный аудит исходников и доступных локальных проверок, не доказательство отсутствия всех ошибок. В этом проходе не проводились браузерная приёмка, нагрузочный тест, аудит продакшен-инфраструктуры, восстановление резервной копии и интеграционные тесты на PostgreSQL.
- Утверждение «не найдено в репозитории» не означает, что соответствующая настройка отсутствует у хостинг-провайдера.

## 6. Архитектура и данные

Сильные стороны: бизнес-логика графа в чистых функциях; раздельные display/radial/pyramid/export модули; server-side роль, приватная выдача медиа; часть операций уже атомарна и имеет ограниченные retries. Тесты сохраняют прежние раскладки.

Зоны роста:

1. `FamilyPerson` используется и для summary, и для detail: пустые `stories/mediaAssets/timeline` могут означать «не загружено», а не «ничего нет». Разделить DTO перед масштабированием.
2. Общий family read загружает всех людей, связи, в том числе биографии/заметки; архив и журнал переиспользуют широкий запрос. Развести read models, замерить payload и SQL.
3. `family-app.tsx` совмещает множество форм и запросов, `family-workspace.tsx` — навигацию, canvas и инспектор. Выделять части по мере выполнения функциональных задач, без массового переписывания.
4. Нет optimistic locking для редактирования карточек. Последняя запись может незаметно затереть правки другого родственника.
5. Внешние ключи Relationship по отдельности не гарантируют принадлежность обеих персон одному familyId. Серверная валидация есть; нужны ограничения БД перед импортом/новыми writers.
6. Redis использует раздельные INCR/PEXPIRE и fallback в память. Нужны атомарность TTL, ограниченные таймауты и явная политика деградации в нескольких инстансах.
7. CSP содержит `unsafe-inline` для scripts. Это возможность усиления, а не доказанный XSS.
8. Медиа полностью читается в память, не поддерживается Range; нужны потоковая выдача, квоты, обработка отказов и согласованное восстановление БД+файлов.

## 7. Эксплуатация и документация

- В репозитории не найден CI workflow, проверяющий каждый предлагаемый набор изменений. Локальное прохождение проверок не заменяет CI.
- Docker Compose поднимает инфраструктуру разработки, не является готовым production deployment приложения. Порты db/redis опубликованы без loopback-привязки; область их доступности зависит от host firewall.
- Не найдены законченные runbook для релиза/отката, совместного backup/restore БД и storage, health/readiness, метрик ошибок и оповещений.
- README содержит устаревающие команды и отличия от package scripts: `db:up` запускает только db, а текст обещает Redis тоже. Не определён воспроизводимый production runtime.
- `docs/sibling-schema-error.tdd.md` документирует применение sibling enum и регистрацию соответствующей миграции вручную, а также незарегистрированную `20260802000000_member_audit_actions`. Это историческое свидетельство необходимости сверки migration history, не результат свежей проверки БД. Нельзя вслепую запускать все миграции.
- В AGENTS факты описаны как parent/spouse, тогда как актуальный код, миграция и тесты поддерживают явно записанный sibling. Последующее указание пользователя заменяет прежний запрет автоматического родительства: spouse/sibling служат основанием для добавления родительских рёбер, пользователь может их исправить. Перед реализацией согласовать AGENTS с GRAPH-01; не создавать фиктивные карточки неизвестных родителей.
- Большой набор изменённых и untracked-файлов принадлежит пользователю. Для будущего релиза нужен согласованный состав поставки; аудит ничего не коммитит и не очищает.
