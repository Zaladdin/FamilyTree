# Релиз и эксплуатация Rodovo

## Воспроизводимая проверка

Проверяемый toolchain: Node **22.19.0**, npm **10.9.3**; версии зафиксированы в `.nvmrc`, `engines`, `packageManager`. `.npmrc` отклоняет несовместимый runtime. При обновлении версий повторить весь протокол, обновить оба package-файла; lockfile не пересоздавать без необходимости.

GitHub workflow `.github/workflows/ci.yml` подготовлен для чистого checkout. Он не содержит production secrets или deploy, имеет только `contents: read`, checkout не сохраняет credentials. Использованы проверенные SHA официальных [checkout v4.2.2](https://github.com/actions/checkout/releases/tag/v4.2.2) и [setup-node v4.4.0](https://github.com/actions/setup-node/releases/tag/v4.4.0). В CI выполняется `npm ci`, локально при подготовке этапа зависимости не переустанавливались.

Задание `quality`: generate → unit → lint → build → typecheck → production smoke. DB URL указывает на недоступный loopback port 1; `.env` с рабочими данными в CI отсутствует. Smoke запускает собственный сервер с синтетической конфигурацией и проверяет контролируемую недоступность БД. Нельзя подменять этот URL адресом рабочего сервера.

Задание `postgres` создаёт отдельный PostgreSQL 16 service без постоянного volume; его публичные учётные данные действуют только внутри одноразового CI job. `npm run ci:database` требует явные `TEST_DATABASE_URL` и `RODOVO_CI_DATABASE=disposable`, разрешает только `127.0.0.1/rodovo_ci_test` без URL options и отклоняет совпадение с текущим `DATABASE_URL`. Только дочерний процесс Prisma получает тестовый URL как DATABASE_URL. После deploy проверяются status, schema diff с ненулевым exit code при расхождении, а также SHA-256 каждого SQL-файла и полнота `_prisma_migrations`. Затем запускаются интеграционные тесты через существующий fail-closed guard. Reset, seed и автоматический `migrate resolve` отсутствуют.

Workflow является подготовленной конфигурацией, а не свидетельством уже успешного запуска GitHub Actions. Перед выпуском сохранить ссылку на реальный зелёный run обоих jobs. Настроить required checks `quality` и `postgres` для защищённой ветки отдельно: YAML сам не включает branch protection. Любая ошибка блокирует приёмку релиза.

## Health и диагностика

- `GET /api/health/live`: 200 с `status: alive`, без обращений к зависимостям.
- `GET /api/health/ready`: 200/503 с `ready`/`not_ready`. Проверяет только
  `SELECT 1`, доступность каталога media и свободное место, Redis при настройке.
  Ответ ограничен таймаутом 1 с на параллельные проверки, кеш — 5 с.
  Незавершённый probe переиспользуется: новые запросы не множат зависшие операции.
- `GET /api/ops/metrics`: подробности только с `Authorization: Bearer …`.
  `OPS_METRICS_TOKEN` должен содержать 32–256 символов A–Z/a–z/0–9/underscore/hyphen;
  отсутствующий или неверный токен возвращает 404 до проверки зависимостей.
  Создание и хранение реального токена относится к настройке среды.
- `OPS_MIN_FREE_STORAGE_BYTES`: минимальное свободное место, по умолчанию 64 MiB.
  Каталог проверяется без записи файлов, включая права чтения/записи/поиска.

Ответы не кешируются HTTP-кешем. Публичная readiness не раскрывает причины,
пути или адреса. API возвращает сгенерированный сервером `x-request-id`.
JSON-логи содержат шаблон маршрута, статус, длительность, безопасную категорию
ошибки и фиксированные события, без payload, cookie и конкретных семейных URL.

Метрики живут в памяти процесса и сбрасываются при рестарте. Длительность API
относится к обработчику, а не полной передаче потокового файла. Backup CLI пишет
события в собственном процессе. Внешний сборщик и доставка оповещений пока не
подключены; события `readiness_degraded`/`redis_degraded` сами по себе не являются
подтверждением получения оповещения оператором. Перед выпуском настроить сбор,
пороговые правила и проверить доставку и восстановление после отказа.

`npm run test:smoke` требует готовую сборку и свободный loopback-порт 3002.
Скрипт запускает собственный Next.js с недоступным тестовым URL БД, синтетическим
storage и токеном, проверяет отказ и очищает только свои временные ресурсы.

## Порядок проверки миграций

Синтетическая проверка перехода с первых двух миграций на текущую схему
выполнена командой `npm run test:upgrade`; результаты и границы:
[приёмка старой схемы](legacy-upgrade-acceptance.ru.md). Она не заменяет
измерения на репрезентативном объёме и отдельную тренировку восстановления.

1. Зафиксировать SHA релиза, версии инструментов, результаты CI и список ожидаемых migrations. Проверить SQL и совместимость кода до/после изменения. Все ранее подготовленные миграции считаются неприменёнными, пока оператор не проверит конкретную среду.
2. На отдельном разрешённом стенде выполнить весь migration chain и восстановление backup по `backup-recovery.ru.md`. Сравнить историю, checksum файлов, фактическую схему и счётчики; проверить медиа и вход тестового пользователя. CI с пустой БД не заменяет проверку обновления существующей базы.
3. Любое расхождение истории, незавершённая миграция или drift — остановка выпуска и отдельная reviewed correction. Не менять уже применённые SQL, не отмечать миграцию выполненной для скрытия проблемы.
4. Перед отдельно разрешённым production deploy согласовать окно, оператора, backup DB+media, измеренную возможность восстановления и предыдущий совместимый артефакт. Автоматического production deploy здесь нет.

## Откат с сохранением новых данных

Предпочитать исправляющий roll-forward. Откат приложения допустим только к проверенному артефакту, который понимает текущую схему и новые состояния данных. В частности, код до media lifecycle может выдать неготовые файлы или потерять cleanup; код до security generation может неправильно обработать отозванные сессии. Такие версии нельзя выбирать для отката без отдельной адаптации.

Учебный протокол выполняется только в disposable стенде: создать синтетическую запись после обновления, сохранить её ID и checksum медиа, переключить на совместимый предыдущий артефакт, выполнить smoke и убедиться, что запись и файл сохранились, затем вернуть текущий артефакт и повторить проверки. Нельзя откатывать SQL удалением таблиц/колонок, reset, truncate или восстановлением старого snapshot поверх новых данных. При аварии остановить запись, сохранить текущее состояние и восстанавливать backup в **отдельную** среду для последующего сверенного переноса новых записей.

Это описанный протокол; реальный учебный откат приложения и PostgreSQL ещё требуется провести. До выбора и проверки совместимого предыдущего артефакта rollback не считается готовым.

## Сеть и локальное хранилище

Compose привязывает PostgreSQL и Redis только к `127.0.0.1`. Стандартные пароли Compose предназначены исключительно для локальной разработки. Для production нужны отдельные credentials, TLS где требуется, закрытая сеть и отсутствие публичных DB/Redis портов; изменение инфраструктуры выполняется отдельной задачей.

Текущий файловый адаптер рассчитан на один пишущий сервер с постоянным volume. Сохранить volume при замене приложения; не включать семейные файлы и `.env` в build/CI artifacts. Несколько пишущих экземпляров требуют отдельно согласованной архитектуры. Backup, restore и cleanup pending записей выполнять по профильным runbooks с остановленными writers, когда это предписано.

## Протокол результата релиза

Записать: SHA, CI run, версии Node/npm, окружение disposable проверки, migration list/checksums, smoke до/после, тест контролируемой потери БД и восстановления, подтверждение приёма оповещения, backup/restore timings и учебный rollback. Не записывать URL БД, токены, семейные payload и приватные пути. Непроведённые проверки отмечать явно; RPO/RTO нельзя считать подтверждёнными без измерений.
