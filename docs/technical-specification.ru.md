# Родово / FamilyTree — техническое задание на завершение и развитие

Версия 1.1, 28 сентября 2026. Статус: предлагаемый объём разработки по результатам [аудита](project-audit-2026-09-28.ru.md), с уточнённым пользователем правилом автоматического родительства. Подготовка документа не является разрешением изменять production, подключать платные сервисы, рассылать письма, применять миграции или публиковать приложение.

Фактическая реализация и ограничения приёмки ведутся отдельно в [журнале прогресса](implementation-progress.ru.md), включая DATA-03 и GRAPH-01. Наличие кода не означает, что миграции применены или изменения выпущены в рабочую среду.

## 1. Назначение и результат

Развить существующее приложение в надёжный закрытый семейный архив: родственники безопасно получают доступ, вводят и исправляют людей и связи, сохраняют воспоминания и оригиналы материалов, могут восстановить данные после ошибки или сбоя.

Сохранить Next.js App Router, React, TypeScript, Prisma/PostgreSQL, русскую локализацию и существующий визуальный язык. Обновление security patches обязательно; переход на новую major-версию, новый state manager, микросервисы или новый тестовый framework не является самостоятельной целью.

Результат первого релиза: закрыты SEC-01/02, DATA-01/02/03 в базовой части, GRAPH-01, AUTH-01/02, MEDIA-01, CONTENT-01, OPS-01/02 и QA-01; существующие возможности работают без регрессий. Остальные требования планируются отдельными этапами.

## 2. Пользователи и права

Базовая матрица сохраняет существующие роли. Новые ограничения чтения отдельных материалов вводятся отдельно по PRIVACY-01, с тестами серверной выдачи.

| Действие | Owner | Admin | Editor | Member | Guest |
|---|---|---|---|---|---|
| Читать доступные семье данные | Да | Да | Да | Да | Да |
| Создавать/редактировать людей, связи, истории, медиа | Да | Да | Да | Нет | Нет |
| Архивировать и восстанавливать людей | Да | Да | Да | Нет | Нет |
| Управлять editor/member/guest | Да | Да | Нет | Нет | Нет |
| Назначать/менять admin | Да | Нет | Нет | Нет | Нет |
| Менять настройки семьи | Да | Да, кроме владения/удаления | Нет | Нет | Нет |
| Передавать владение, окончательно удалять пространство | Да | Нет | Нет | Нет | Нет |
| Экспортировать изображение доступного дерева | Да | Да | Да | Да | Да |
| Полная резервная выгрузка и импорт | Да | По отдельному разрешению владельца | Нет | Нет | Нет |

Все проверки выполняются сервером. Наличие скрытой кнопки не является механизмом защиты. Матрица должна покрывать как API, так и server-rendered страницы, медиа и экспорт. Передача владения не должна оставлять семью без владельца.

## 3. Обязательные инварианты

1. Родительские связи создаются вручную и автоматически на основании супружества и связи «брат/сестра». По умолчанию супруг становится вторым родителем ребёнка, а братья/сёстры получают общих уже известных родителей. Пользователь может исправить или удалить автоматически добавленную связь. Подробные правила и разрешение конфликтов — GRAPH-01.
2. Поддержать существующие parent/spouse/sibling. Автоматически добавленные parent сохраняются как обычные редактируемые рёбра с указанием происхождения. Вычисляемые «тесть», «невестка» и другие подписи не сохраняются как отдельные рёбра.
3. Нет self-link, parent-cycle и межсемейных ссылок. Симметричные spouse/sibling не дублируются при обратном направлении.
4. До введения типов родительства сохранить действующее ограничение двух родителей, включая архивных. Его изменение — отдельная миграция модели по GENEALOGY-01.
5. Сохранить круговой вид по умолчанию, выбранного человека в центре, детерминированность, компактные круговые контекстные узлы, единственный «Скрыть остальных», zoom к выбранному, «Снять выбор»/Escape и нативный мини-диалог добавления.
6. Пирамидальный вид, перемещение и экспорт сохраняются. Рёбра отражают точные записанные связи и доходят до границы кружков.
7. Архивирование скрывает человека, но не уничтожает факты родства. Восстановление возвращает его исходные материалы и связи.
8. Внутри мутации данные, счётчики и аудит согласованы. Неуспешная операция не оставляет половину графа.
9. Не выводить токены, cookie, SQL, connection string, личные данные в диагностические ответы или общие логи.
10. Только disposable TEST_DATABASE_URL для интеграционных тестов. Никаких reset/seed/fixtures в реальном DATABASE_URL.

## 4. Требования первого этапа

### SEC-01 — безопасные зависимости, P0

Основание A01. Проверить package.json, lockfile и фактически собранный runtime. Выбрать актуальную исправленную совместимую версию Next.js и соответствующие React/react-dom/eslint-config-next; отдельно проверить транзитивные advisories. Зафиксировать версии lockfile. Не заменять это только обновлением npm audit summary.

Приёмка: для поставляемых версий нет непринятых применимых critical/high advisory; unit/tsc/lint/build проходят; на disposable стенде проверены регистрация, вход, SSR семьи, загрузка и экспорт. Документированы версии, дата проверки и оставшиеся исключения. Старый артефакт доступен для отката к безопасной версии; откат к заведомо уязвимой сборке не считается безопасным решением.

### SEC-02 — единый контракт ошибок API, P1

Основание A05. Распространить безопасную границу `familyWriteErrorResponse` или совместимый mapper на все API. Формат ошибки: `{ error, code, requestId, fieldErrors? }`; error — безопасный русский текст. HTTP: 400 формат/валидация, 401 сессия, 403 права, 404 отсутствующий ресурс, 409 конфликт, 413 размер, 429 частота, 500 неизвестный сбой, 503 временная недоступность зависимости. Политика 403/404 для чужих ресурсов должна быть единообразной и не раскрывать их существование.

Клиент сохраняет форму после ошибки, связывает ошибки с полями, не повторяет мутацию автоматически. После неизвестного исхода запроса предлагает проверить результат; для повторяемых операций использовать ключ идемпотентности, привязанный к пользователю/семье и hash payload. Ошибка самого логгера не должна разрушать ответ.

Приёмка: во все группы маршрутов внедрены синтетические ошибки Prisma/fs/JSON; только доменные сообщения видны клиенту, SQL/пути/stack отсутствуют. Отсутствие БД не выдаётся за ошибку пользователя. RequestId находится в обезличенном серверном журнале. Существующий SIBLING_SCHEMA_NOT_READY продолжает корректно обрабатываться.

### DATA-01 — идентификаторы и дубли, P1

Основание A02. Генерировать глобально уникальные ID в single и batch сохранении; planner может сохранять временные локальные ID, но persistence обязан переназначить все ссылки. Старые ID и deep links не менять массово.

Приёмка: одинаковые ФИО/дата в двух семьях создаются без конфликта; повтор внутри одной семьи обрабатывается по действующей политике дублей; все новые рёбра и audit personId указывают на окончательный ID; batch откатывается целиком при ошибке одного участника. Добавить тест реального PK на отдельной тестовой БД, поскольку моки не моделируют глобальную уникальность.

### DATA-02 — корректные и неполные даты, P1; расширение P2

Основания A03/A10. Сначала исправить MM.YYYY и проверку порядка дат. Ввести общую модель даты для UI, API, поиска дублей, сортировки, экспорта и layout. Предлагаемые поля: исходный текст, qualifier (`exact/approximate/before/after/range/unknown`), точность (`year/month/day`), nullable компоненты даты, начало/конец диапазона. Не подставлять 1 января для неизвестного дня.

Базовый релиз: валидные YYYY, YYYY-MM, YYYY-MM-DD, MM.YYYY, DD.MM.YYYY, неизвестные даты рождения/смерти и место рождения. Эквивалентные полные даты сравниваются одинаково. Интервальные проверки отклоняют только доказанное противоречие; неоднозначность выдаёт предупреждение. Расширенные qualifiers — второй этап.

Миграция: сначала отчёт классификации старых строк и конфликтов; неизвестные форматы сохраняются без потери оригинала. Добавить новые поля, выполнить контролируемый backfill, проверить чтение, затем отдельно решить удаление старых. Не объединять людей автоматически.

Приёмка: 13.1900 и 31.02.2000 отклонены; 29.02.2000 принят, 29.02.1900 отклонён; смерть 1900-04 при рождении 05.1900 отклонена; равные полные даты разных форматов дают одинаковое нормализованное значение; неизвестный день не становится известным; человек с неизвестной датой сохраняется и экспортируется без фиктивной даты.

### DATA-03 — конкурентные изменения, P1/P2

Основания A08/A11/A13 и отсутствие ревизий. Проверять инварианты внутри сериализуемой транзакции/согласованной блокировки. Повторы ограничены и повторяют весь read-validate-write. Защитить archive/restore, управление ролями и лимит семей. Авторизацию проверять с актуальными ролями там, где конкуренция меняет полномочия.

Ввести `version` или иной устойчивый concurrency token карточки/истории; PATCH требует ожидаемую ревизию, конфликт возвращает 409 и сохранённый пользовательский черновик. Архивирование, восстановление и удаления должны иметь определённое поведение при повторном запросе.

Приёмка: два параллельных архивирования последних двух людей оставляют хотя бы одного активного; при 9 семьях параллельные создания дают не больше 10; обычный admin не меняет уже повышенного admin; два редактора не перезаписывают данные незаметно. Счётчики и аудит после конкуренции соответствуют фактам. Все сценарии — на отдельной PostgreSQL БД, не только в mock tests.

### GRAPH-01 — автоматическое родительство и исправление связей, P1

Основание A04 и уточнение пользователя: супружество и sibling должны по умолчанию означать родительство, а исключения пользователь исправляет сам. Привести single API, batch и формы к одинаковому поведению: автоматическое добавление родителей не зависит от наличия или отсутствия `additionalRelationships`. Сохранить возможность указать родителей вручную.

Правила автоматического добавления:

- При добавлении ребёнка человеку с одним супругом записать обоих супругов родителями. При добавлении супруга связать его с уже записанными детьми другого супруга как второго родителя, если соответствующее место свободно.
- При добавлении sibling перенести известных родителей одного брата/сестры другому; если сведения есть у обоих, дополнить недостающие связи в обе стороны в пределах ограничений. Если родители не известны ни у одного, сохранить sibling без создания фиктивных карточек родителей. При последующем добавлении родителя предложенное правило применяется и к связанным братьям/сёстрам.
- Существующие явно назначенные родители и пользовательские исправления имеют приоритет. При нескольких возможных супругах, превышении двух родителей или несовместимости графа сохранить допустимую исходную связь и показать, какие родительские связи не добавлены и требуют выбора пользователя. Не заменять уже записанного родителя автоматически.
- Добавление допустимых автоматических рёбер выполнять вместе с исходной операцией в транзакции. При распространении по нескольким sibling-связям обход ограничивать посещёнными узлами; не создавать дубли, циклы или межсемейные связи.
- Для каждого автоматического ребра сохранять происхождение и основание в данных/аудите; в интерфейсе показывать «Добавлено автоматически» и действия исправления/удаления. Отдельное подтверждение каждой бесконфликтной связи не требуется.
- Пользовательское удаление или замена автоматической связи сохраняет исключение: последующая загрузка дерева, повтор запроса или редактирование соседнего человека не восстанавливают отменённое родительство. Возобновить его можно явным действием пользователя. Так поддерживаются неполнородные братья/сёстры и дети от других браков.

Добавить просмотр списка записанных связей, редактирование и удаление конкретной связи. Перед сохранением показывать человеку понятное описание изменения. Удаление связи не удаляет людей и материалы. В API возвращать стабильный relationshipId либо документированный ключ ребра; преобразование типа делать атомарно с повторной валидацией графа и аудитом.

Приёмка: запросы с отсутствующим и пустым `additionalRelationships` дают одинаковые автоматические связи; ребёнок человека с единственным супругом получает двух родителей; новый супруг получает допустимые родительские связи с существующими детьми; sibling получает уже известных родителей, в том числе добавленных позднее. При неизвестных родителях фиктивные люди не создаются. Ошибочного родителя можно заменить или удалить, и после перезагрузки/повторных операций исправление сохраняется. Несколько супругов и занятые родительские места дают понятный конфликт без перезаписи. Обратные spouse/sibling не дублируются; архивные предки учитываются в циклах/лимитах; после изменения пересчитываются подписи и обе раскладки. Смена перспективы сама по себе не пишет данные. Сохранить и расширить тест автоматического назначения супруга родителем; добавить регрессии sibling, ручных исключений и одинакового поведения single/batch/UI.

### AUTH-01 — подтверждение email и приглашения, P1

Основание A06. Добавить `emailVerifiedAt`, одноразовые токены подтверждения с хранением только hash и сроком действия. Предлагаемый TTL подтверждения 24 часа, приглашения 7 суток — параметры конфигурации. Приглашение связано с familyId, нормализованным email, ролью, пригласившим и статусом pending/accepted/revoked/expired.

Получатель подтверждает адрес и явно принимает приглашение. Пересланная ссылка не даёт членство аккаунту с другим адресом. Повторное принятие идемпотентно; отзыв и смена роли до принятия учитываются. Нельзя назначать owner через приглашение; admin не назначает admin.

Переход существующих аккаунтов: старые email не считать автоматически подтверждёнными. Разделить legacy-членства и новые приглашения; согласовать период повторного подтверждения и процедуру восстановления владельца до включения ограничений. Существующий доступ не отключать массово без проверенного способа восстановления, но выдачу новых прав по неподтверждённому адресу прекратить. На стенде проверить владельца и участника, созданных до миграции, недоступный прежний адрес и попытку захвата legacy-аккаунта; переезд не должен ни молча подтвердить чужую почту, ни оставить архив без управляющего.

Приёмка: регистрация на чужой email без доступа к почте не получает приглашённое членство; просроченный/отозванный/повторно использованный токен безопасен; гонка двух accept не создаёт дубль. Токены отсутствуют в логах и analytics. Отправку писем тестировать локальным адаптером; внешний email-провайдер и реальные письма — отдельное согласование.

### AUTH-02 — восстановление доступа и сессии, P1

Добавить «Забыли пароль», установку нового пароля по одноразовой ссылке, смену пароля из профиля с проверкой текущего, завершение других сессий. Внешний ответ на запрос сброса одинаков для существующего и неизвестного email. Ограничения по адресу/IP, TTL сброса по умолчанию 30 минут.

Приёмка: reset-токен используется один раз, хранится hash; после смены пароля старые сессии отозваны, текущая политика выдачи новой сессии определена; повторный submit не меняет пароль дважды; новая сессия имеет Secure/HttpOnly/SameSite; при ошибке доставки система не раскрывает существование аккаунта.

### CONTENT-01 — законченный цикл историй и карточки, P1/P2

Основания A09/A14. Добавить PATCH/DELETE истории с ревизиями и аудитом; удаление сначала мягкое с возможностью восстановления. Сохранять абзацы биографий/историй/заметок; ограничивать длину, но не применять к многострочному тексту нормализацию имён. Выводить plain text безопасно, без произвольного HTML.

Автоматические события рождения/смерти вычислять из карточки либо помечать как системные и синхронизировать; пользовательские события не перезаписывать. Добавить предупреждение о несохранённой форме при закрытии/навигации без блокировки успешного сохранения.

Приёмка: история создаётся, редактируется, удаляется и восстанавливается с корректным счётчиком; переносы сохраняются после повторной загрузки; изменение рождения не оставляет противоречащую автоматическую строку; пользовательская хронология сохраняется; member/guest не меняют историю прямым HTTP-запросом.

### MEDIA-01 — надёжное приватное хранилище, P1

Основания A07/A12. Определить единственный storage adapter: сохранить локальный persistent volume для одного сервера либо отдельно выбрать объектное хранилище для нескольких. Не привязывать доменную модель к публичному URL. Доступ к оригиналу всегда проверяется.

Ограничивать фактические байты запроса до полного разбора; документировать proxy body limit. Сохранить лимиты фото 10 MiB, аудио 20 MiB, установить квоту семьи и суммарную квоту системы. Резервирование квоты атомарно, не обходится параллельными uploads.

Для согласования БД и файла использовать состояния pending/ready/deleting/failed и повторяемую задачу удаления/компенсации, которую можно выполнять в существующем приложении без отдельного брокера. Нужны bounded retries, журнал неудач и диагностическая сверка orphan/missing files. Не удалять найденные неизвестные файлы автоматически.

Приёмка: oversized multipart без Content-Length и с несколькими частями получает 413 без записей и файлов; неподходящий формат отклоняется; отказ БД после upload и отказ FS после удаления не теряют возможность очистки; рестарт приложения не теряет ready-файл. Проверены IDOR, path traversal и отозванное членство. Аудио выдаётся потоково с корректными Range/206 и 416; многократная загрузка не буферизует целиком большие файлы на каждый GET.

### OPS-01 — резервное копирование и восстановление, P1

Подготовить runbook для согласованного backup БД и оригиналов media с manifest/checksum. Копия хранится отдельно от рабочего диска, доступ ограничен, секреты не входят в пользовательский экспорт. Срок хранения и объём фиксируются после выбора инфраструктуры.

Предлагаемые начальные цели, не текущие измерения: RPO не более 24 часов, RTO не более 4 часов для согласованного небольшого семейного архива. До обещания этих значений провести тренировку.

Приёмка: из копии восстановлены отдельная БД и отдельное storage без доступа к production; сверены количество людей/связей/историй, хеши материалов и доступ тестового пользователя. Оформлен протокол с временем и обнаруженными потерями. PNG/PDF не считается backup.

### OPS-02 — воспроизводимый релиз и наблюдаемость, P1

Зафиксировать поддерживаемые Node/npm, проверенную установку из lockfile, шаги generate/test/tsc/lint/build. Добавить CI с disposable PostgreSQL, отдельными секретами и fail-closed guard. Сборка и smoke должны работать на синтетических данных без чтения production.

Разделить liveness и readiness; проверять доступность зависимостей с timeout без вывода секретов. Логи включают requestId, категорию, длительность и код ошибки, но не payload семейных историй. Добавить метрики 5xx/latency, свободного storage, неудачных uploads/cleanup/backup, состояния Redis. События деградации не должны молча исчезать.

Перед релизом отдельно сверить migration history со схемой; подготовить reviewed migration, backup, критерии остановки и rollback/roll-forward. Не выполнять `migrate resolve` для сокрытия несоответствий. Описать локальное bind db/redis к loopback и production network isolation.

Приёмка: чистый checkout собирается в CI; ошибка тестов блокирует выпуск; потеря БД даёт контролируемый статус, срабатывает проверяемое оповещение; учебный откат не удаляет новые данные; после восстановления сервис проходит smoke. Реальный deploy выполняется только после отдельного разрешения.

### QA-01 — сквозная приёмка, P1

Сохранить node:test и существующие регрессии. Для UI использовать установленный Codex browser/CUA и in-memory preview на 3001; для полной авторизации/БД — отдельный disposable стенд без auth bypass. Новый Playwright/CDP/MCP не устанавливать автоматически.

Обязательные сценарии: регистрация/вход/сброс, создание семьи и первого человека, single/batch, автоматические родители через spouse/sibling, ручное назначение и исправление родителей, сохранение исключений для нескольких браков и half-siblings, изменение/удаление связи, история, upload/delete/range, archive/restore, роли/чужая семья, поиск/zoom/перспектива, круг/пирамида, export PNG/PDF, конфликты редакторов и отказ сети.

Приёмка UI: 360/390/768/1440 px, клавиатура, видимый фокус, возврат фокуса из диалога, Escape, 200% zoom, отсутствие горизонтального скролла у форм, доступные названия, чтение ошибок screen reader. Canvas может иметь собственную навигацию. Отсутствие console errors и корректные empty/loading/error/permission states проверяются фактически, а не только SSR-строками. Финальный отчёт перечисляет браузер, viewport, сценарий и результат; процент покрытия не заявляется без измерения.

## 5. Второй этап: полнота архива

### GENEALOGY-01 — модель реальных семей, P2

Добавить неизвестный пол/неуказанное значение без принуждения к выдуманным данным, предыдущие фамилии и варианты имени; отделить историю союза (начало/конец, действующий/завершённый/неизвестно) от parent edge. Для родительства определить biological/adoptive/guardian и соответствующие правила числа родителей. Не выводить тип существующих связей автоматически: они получают legacy/unspecified.

Приёмка: повторный брак применяет правила автоматического родительства GRAPH-01 к существующим детям, сохраняя ручные исключения и не создавая новые карточки детей; бывший супруг отличается от действующего по данным; биологические и приёмные отношения не смешиваются в подписях; неизвестные сведения не пропадают при экспорте; старые записи читаются до и после миграции. Расширение kinship на дальние степени должно показывать путь по записанным связям и разрешать несколько вариантов родства, включая пометки об автоматически созданных родительских рёбрах.

### ARCHIVE-01 — документы, события и источники, P2

Добавить приватный document asset (первый формат PDF), метаданные автора/даты/места/описания и ссылку на оригинал; безопасную выдачу и отдельные лимиты. Source хранит вид, заголовок, архивный шифр/URL, цитату и заметку. FactSource связывает источник с человеком/событием/связью и степенью достоверности.

Пользовательские события: тип, дата с точностью, место, описание, участники и источники. Материал может относиться к нескольким людям без копирования оригинала; разрешения проверяются для каждой выдачи.

Приёмка: документ загружается/читается/удаляется как приватный объект, documentsCount отражает факты; два источника могут противоречить и сохраняются оба; источник отображается рядом с подтверждаемым фактом; удаление одной привязки не удаляет общий файл.

### PORTABILITY-01 — переносимый экспорт, импорт и дубли, P2

Добавить versioned JSON+manifest+оригиналы media для полного экспорта и восстановления. GEDCOM — отдельный адаптер с зафиксированной поддерживаемой версией и перечнем потерь, а не обещание безусловного round-trip любого файла. До реализации проверить официальную спецификацию выбранной версии.

Импорт: лимиты и безопасная распаковка, dry-run, отчёт ошибок, предварительное сопоставление людей, явное подтверждение merge, идемпотентность партии, атомарность либо документированные checkpoints. Запрет межсемейных ссылок и архивных parent-cycles сохраняется. Merge показывает конфликтующие поля/источники, переназначает связи и материалы, имеет журнал и обратимый результат в пределах принятой политики.

Приёмка: экспорт синтетической семьи восстанавливает все поддерживаемые данные и хеши media; повторный импорт не удваивает записи; архив с path traversal/zip bomb отклонён; идентичные ФИО не объединяются автоматически; несовместимые данные видны в отчёте до записи.

### COLLAB-01 — журнал, настройки и владение, P2

Cursor pagination журнала с устойчивым `(createdAt,id)`, фильтры по действию/человеку/исполнителю/периоду. В AuditLog добавить actorUserId, entityType/entityId, action, requestId, revision и безопасный структурированный diff. Ограничить чтение чувствительного diff; аудит не заменяет backup.

Разрешить смену названия/описания/региона без разрушения slug-ссылок, редактирование профиля, передачу владения подтверждённому участнику после повторной аутентификации владельца. Существующий выход обычного участника через удаление собственного членства сохранить и покрыть регрессией. Окончательное удаление — отдельная подтверждаемая операция с периодом восстановления.

Приёмка: 250 событий доступны без пропусков/дублей; новый action не маскируется как person_created/person_updated; одинаковые имена исполнителей различимы; владелец не выходит без передачи; два конкурентных переноса не оставляют ноль владельцев. Исторический actorName сохраняется как снимок.

### PRIVACY-01 — управление видимостью, P2

До реализации определить: кто видит полные даты живых людей, заметки, документы, аудио и журнал. Рекомендуемая стартовая политика — всё закрыто вне семьи; отдельный материал может быть ограничен owner/admin; guest видит только разрешённую семейную проекцию. Не вводить публичные share links по умолчанию.

Приёмка: закрытое поле отсутствует в HTML, RSC payload, JSON, поиске, media и экспорте, а не только скрыто CSS; отзыв доступа действует на новые серверные запросы; поведение кеша и TTL download-ссылок документировано. Уже скачанные пользователем копии технически отозвать нельзя. Политика обработки и удаления персональных данных формулируется после определения аудитории/юрисдикции, без заявления юридической сертификации.

### UX-01 — поиск, навигация и сохранение вида, P2

Развить существующий список людей как доступную альтернативу canvas: добавить фильтры и постраничную навигацию при больших объёмах. Расширить поиск по фамилии/вариантам имени/месту/историям, сохранить переход к архиву/участникам/журналу даже из пустой семьи. Смещения и настройки вида сохранять в версии пользовательской настройки по user/family/perspective/mode. При изменении графа удалять устаревшие offsets безопасно; координаты по умолчанию детерминированы.

Приёмка: после перезагрузки согласованные настройки восстановлены; один пользователь не переставляет дерево другому; сброс возвращает автоматический вид; удалённый personId не ломает layout; нет результатов из чужой семьи; поиск работает клавиатурой и показывает отсутствие совпадений.

### PERF-01 — масштаб и read models, P2

Разделить FamilyGraphSummary, PersonDetail, ArchivePage и JournalPage. Не загружать все биографии и материалы для первоначального canvas; пагинация списков, lazy detail, измерение запросов и размера RSC. Оптимизация графа только после профилирования. Микросервисы/Redis-кеш не требуются заранее.

Предлагаемый профиль приёмки: 1 000 людей, 2 000 связей, 10 000 metadata-записей материалов на синтетической семье; базовый сервер 2 vCPU/4 GB и отдельно зафиксированный браузер/устройство/сеть. Цели после прогрева: p95 API чтения ≤500 мс, запись без передачи файлов ≤1 с при 20 активных сессиях; выбор человека в уже загруженном дереве ≤200 мс. Эти значения — план, не измеренная производительность. Для 5 000 людей сначала исследование и согласование UX ограничения.

Приёмка: воспроизводимый отчёт о данных, окружении, payload, p50/p95, SQL и памяти; нет межсемейного кеша; деградация крупных графов сообщает ограничение и позволяет найти человека.

## 6. Изменения схемы и API

Предлагаемые сущности: EmailVerificationToken, PasswordResetToken, FamilyInvitation, ревизия Person/Story, structured genealogical date, Relationship metadata/Union, происхождение автоматических связей и сохранённые пользовательские исключения, Source/FactSource, Media lifecycle, Audit actor/entity/diff, UserTreePreference, ImportBatch. Точные имена и поля уточняются перед соответствующим этапом; вводить всё сразу не нужно.

Базовые новые маршруты (контракт предложения):

| Группа | Маршруты/действия | Основное ограничение |
|---|---|---|
| Аккаунт | POST auth/forgot-password, reset-password, verify-email, PATCH account/password, DELETE account/sessions | TTL, одноразовость, rate limit, Origin |
| Приглашения | POST/GET family/:slug/invitations, DELETE invitations/:id, POST invitations/:token/accept | Verified email, актуальная роль, токен не логировать |
| Родство | PATCH/DELETE family/:slug/relationships/:id | Внутрисемейность, revision, инварианты графа |
| Истории | PATCH/DELETE/restore people/:personId/stories/:id | Права, версия, аудит |
| Журнал | GET family/:slug/journal?cursor=... | Права, стабильная пагинация, лимит страницы |
| Настройки | PATCH family/:slug, POST ownership-transfer, POST leave | Защита владельца и повторная аутентификация |
| Перенос | POST exports, GET exports/:id, POST imports/preview, POST imports/:id/commit | Квоты, owner permission, TTL и подтверждение preview |

Все payload валидируются существующим стилем runtime-validation или отдельно согласованной библиотекой. Описать лимиты полей, статус-коды, допустимые переходы состояния, повтор запросов и примеры ошибок; стабильные machine-readable code отделить от русских сообщений.

Миграции: additive-first → совместимое чтение → контролируемый backfill → проверка → переключение → удаление legacy отдельным релизом. Каждый этап включает схему до/после, индекс, оценку блокировок, test migration, backup и способ восстановления. Для индексов/constraints предварительно выявлять существующие нарушения. Новые пользовательские операции применяют автоматическое родительство по GRAPH-01. Массовое достроение связей в уже существующих родословных оформляется отдельным backfill с предварительным отчётом и возможностью отката; изменение ТЗ само по себе не запускает его.

## 7. План работ и зависимости

Оценки — относительный размер: S небольшая локальная задача, M несколько связанных модулей, L схема+API+UI+проверки. Это не обещание календарного срока. Каждый этап при реализации дробится на небольшие проверяемые изменения.

| Этап | Контекст и результат | Зависимости | Размер | Выходной критерий |
|---|---|---|---|---|
| 1 | SEC-01: обновить уязвимый runtime, сохранить архитектуру | Нет | M | Исправленный пакетный состав и регрессии |
| 2 | DATA-01, базовый DATA-02, подготовка GRAPH-01: идентификаторы, парсер, единые правила автоматического родительства и тесты | 1 | M | Регрессии ID/дат проходят; контракт автоматических связей подготовлен |
| 3 | SEC-02, DATA-03: единые ошибки, атомарность и конфликты | 2 | L | HTTP и PostgreSQL concurrency-тесты |
| 4 | GRAPH-01, CONTENT-01: автоматические родители вместе с исправлением/удалением и сохранением исключений; истории/хронология | 2, 3 | L | Полные циклы на стенде; автосвязи не выпускаются без возможности исправления |
| 5 | AUTH-01/02: email ownership, приглашения, восстановление | 1, 3 | L | Проверенные негативные auth/role сценарии |
| 6 | MEDIA-01, OPS-01: файлы, лимиты, компенсация, backup/restore | 3 | L | Fault injection и тренировка восстановления |
| 7 | OPS-02, QA-01: CI, эксплуатация, приёмка релиза | Начать после 1; завершить после 4–6 | L | Протокол релиза без открытых P0/P1 |
| 8 | GENEALOGY-01, ARCHIVE-01, расширенный DATA-02 | 4, 6, 7 | L | Совместимые миграции и источники фактов |
| 9 | COLLAB-01, PRIVACY-01, UX-01, PERF-01 | 5, 7; полевая модель 8 при необходимости | L | Права/журнал/поиск/профилирование |

Независимо можно готовить CI, интерфейс error mapper и протокол backup. После согласования общих схем/API этапы 4–6 могут выполняться параллельно разными исполнителями; изменения Prisma и auth координируются одним владельцем. Перед каждым этапом перечитать актуальные AGENTS, relevant modules и тесты: рабочая копия продолжает изменяться.

Для каждого изменения: воспроизводимая регрессия → минимальная реализация → профильный review → scoped проверки → общие проверки. Возврат: feature flag/откат к совместимой безопасной сборке; данные новых форматов не удалять обратной миграцией без отдельной проверки.

## 9. Решения, необходимые до соответствующих этапов

1. Один семейный сервер или многопользовательский сервис: определяет хостинг, квоты, RPO/RTO и provider email/storage. Базовое предположение ТЗ — закрытый сервис с несколькими независимыми семьями.
2. Email delivery и storage provider, бюджет и расположение данных. До выбора использовать адаптеры и локальные test doubles.
3. Различие member/guest, видимость сведений о живых людях, права на полную выгрузку.
4. Допустимые типы родительства и союзов; как объяснять неопределённость и противоречащие источники.
5. Срок мягкого удаления, хранения backup, аудита и экспортных файлов.
6. Целевая величина дерева и устройства; численные performance-цели подтвердить замером.
7. Поддерживаемая версия GEDCOM и допустимые потери на границе форматов.

Эти решения не мешают начинать исправления SEC-01/02, DATA-01/02, реализацию автоматического родительства с пользовательскими исправлениями и подготовку CI. OCR, AI-биографии, транскрибация, календарь напоминаний, публичные страницы, платежи и мобильные клиенты остаются вне базового объёма.
